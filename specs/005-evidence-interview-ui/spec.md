# Feature Specification: Экраны доказательного техинтервью

**Feature Branch**: `005-evidence-interview-ui`

**Created**: 2026-09-03

**Status**: Draft

**Input**: Спецификация экранов (чат), `PRODUCT.md` кейса, прототип Napoleon (`App.jsx`, `tokens.css`, `app.css`)

## Синхронизация с кодом

`frontend/` сейчас пустой каркас Next.js: стартовая страница и заглушка `/interview/[token]`.
Экраны рекрутёра, кандидата, эксперта и менеджера отсутствуют.

Этот спек описывает **только интерфейс**. Данные для демо живут во фронте.
Бэкенд и live-агент не меняются.

Спеки [[003-recruiter-vacancy-management]] и [[004-candidate-interview-flow]] описывают
другой продукт (живое видеоинтервью с баллами). Для хакатонного демо источником правды
по экранам является этот документ. Код в `frontend/` должен соответствовать ему.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Кандидат проходит асинхронное интервью (Priority: P1)

Кандидат открывает ссылку без пароля, понимает правила, даёт согласие, проверяет
микрофон, отвечает на вопросы голосом или текстом, при необходимости отвечает на одно
уточнение и видит экран «Интервью отправлено».

**Why this priority**: без этого пути нельзя показать жюри основной сценарий кандидата.

**Independent Test**: с демо-токеном пройти C1 → C2 → C3 → C4 → C5 → C6 (вопрос 3) → C7 → C9.
На узком экране C1 предлагает прислать ссылку на почту; с C3 при ширине меньше 900 px
показывается «Откройте с ноутбука».

**Acceptance Scenarios**:

1. **Given** валидная ссылка, **When** кандидат открывает её, **Then** видит C1: вакансия, факты, правила, кнопка «Начать».
2. **Given** C2, **When** не отмечен обязательный чекбокс, **Then** «Продолжить» неактивна.
3. **Given** C6 в состоянии подготовки, **When** таймер доходит до нуля, **Then** запись сама не стартует.
4. **Given** ответ сохранён и нужно уточнение, **When** проходит не больше нескольких секунд, **Then** открывается C7; иначе следующий вопрос или C9.
5. **Given** сессия прервана, **When** кандидат возвращается по ссылке, **Then** видит C8 и может продолжить.

---

### User Story 2 - Рекрутер разбирает отчёт и принимает решение (Priority: P1)

Рекрутер входит как демо-роль, открывает вакансию, видит канбан, открывает отчёт
неоднозначного кандидата, читает доказательства, запрашивает доп. ответ и фиксирует решение.

**Why this priority**: это главный экран продукта и обязательный кусок демо.

**Independent Test**: S1 → R3 → карточка неоднозначного кандидата → R5 → drawer
«Недостаточно данных» → R6 → панель решения → «Посмотреть как менеджер» (M4).

**Acceptance Scenarios**:

1. **Given** R3, **When** рекрутер смотрит доску, **Then** пять колонок и три демо-кандидата: сильный, слабый, неоднозначный.
2. **Given** R5, **When** открыт отчёт, **Then** рекомендация системы только в серой плашке «Система предлагает», без процентов уверенности.
3. **Given** клик по требованию, **When** открывается drawer, **Then** видны вывод, цитата с таймкодом, «почему такой статус» и следующее действие.
4. **Given** решение нажато, **When** панель обновилась, **Then** видно «Решение: …» с именем и датой; старая запись не стирается.

---

### User Story 3 - Рекрутер ведёт вакансии и приглашает кандидата (Priority: P2)

Рекрутер видит таблицу вакансий, создаёт вакансию за три шага (извлечение имитируется),
приглашает кандидата из модального окна.

**Why this priority**: нужно для полного контура рекрутёра, но демо можно начать с готовой вакансии.

**Independent Test**: R1 (вкладки статусов, пустое состояние) → R2 (извлечение через 2 секунды) → R4 (тост «письмо отправлено» + ссылка).

**Acceptance Scenarios**:

1. **Given** нет вакансий, **When** открыт R1, **Then** пустое состояние и кнопка «Новая вакансия».
2. **Given** шаг 1 в R2, **When** нажато «Извлечь требования», **Then** через короткую паузу появляется готовый результат для Middle+ Python.
3. **Given** R4, **When** нажато «Отправить приглашение», **Then** письмо не уходит наружу: тост и возможность скопировать ссылку.

---

### User Story 4 - Эксперт и менеджер, служебные экраны (Priority: P2)

Жюри может открыть рубрику и комплект вопросов только для чтения, одностраничник
менеджера, вход с выбором роли и служебные страницы.

**Why this priority**: показывает, откуда взялась рубрика и что видит менеджер.

**Independent Test**: E2 и E4 read-only; M4 печатаемый одностраничник; S1 выбор роли; S2 для 403/404/истекшей ссылки.

**Acceptance Scenarios**:

1. **Given** E2/E4, **When** эксперт пытается править, **Then** поля не редактируются, утверждение неактивно с текстом «В демо рубрика утверждена заранее».
2. **Given** M4, **When** страница открыта, **Then** прокторинга нет; есть «подтверждено», «о чём поговорить», одна сильная сторона, кнопки после встречи.
3. **Given** S1, **When** выбран вход, **Then** это демо-кнопки ролей, не настоящая почта.

---

### User Story 5 - Пилот-экраны как статичные макеты (Priority: P3)

Экраны с меткой «Пилот» открываются по маршрутам, показывают правдоподобный макет,
но без полной рабочей логики.

**Why this priority**: жюри видит следующий шаг продукта, не путает его с рабочим MVP.

**Independent Test**: открыть каждый пилот-маршрут и убедиться, что экран читается и помечен как макет.

**Acceptance Scenarios**:

1. **Given** пилот-экран, **When** пользователь открывает его, **Then** виден полный макет по спецификации и явная пометка, что это пилот.
2. **Given** C11 (позже), **When** маршрут открыт, **Then** короткая заглушка «будет после пилота», не полный редактор транскрипта.

### Edge Cases

- Ссылка истекла → `/i/expired` с датой и email рекрутера.
- Интервью уже отправлено → C9.
- Нет доступа к микрофону → инструкция и повтор; либо текстовый режим на все вопросы.
- Ошибка сети во время интервью → полоса сверху, не отдельная страница.
- Слова «списывание», «обман», «подозрительно» нигде не появляются; прокторинг = «событие».
- Проценты уверенности модели никому не показываются.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Кандидатские экраны MUST быть одной колонкой максимум 720 px, с `Stepper` и одной главной кнопкой.
- **FR-002**: Внутренние роли MUST иметь левую навигацию 200 px и рабочую область; макет 1280, минимум 1024.
- **FR-003**: Статусы требований MUST использовать словарь дословно и компонент `StatusBadge`.
- **FR-004**: Рекомендация системы MUST быть только в серой плашке `AiNote` с подписью «Система предлагает».
- **FR-005**: Решение человека MUST быть в цветной плашке `HumanNote` с именем и датой.
- **FR-006**: `EvidenceLink` MUST открывать фрагмент по таймкоду; если цитаты нет в транскрипте, ссылка неактивна и рядом текст «цитата не подтверждена транскриптом».
- **FR-007**: Проценты уверенности модели MUST NOT показываться ни на одном экране.
- **FR-008**: Кнопки MUST быть глаголом в инфинитиве («Передать менеджеру»), не «ОК» и не голое «Далее».
- **FR-009**: В MVP письма MUST имитироваться тостом; приглашение создаёт копируемую ссылку.
- **FR-010**: Извлечение требований в R2 MUST показывать заранее подготовленный результат для Middle+ Python после паузы около 2 секунд.
- **FR-011**: Три демо-кандидата MUST быть: сильный (Соответствует, 6/6), слабый (Не соответствует, 2/6), неоднозначный (Недостаточно данных, 4/6, цитата не найдена, одно событие прокторинга).
- **FR-012**: E2 и E4 в MVP MUST быть только для просмотра.
- **FR-013**: Пилот-экраны MUST открываться по своим маршрутам как статичные макеты.
- **FR-014**: Служебные экраны `/403`, `/404`, `/i/expired` MUST существовать с текстами из спецификации.
- **FR-015**: В демо MUST быть вход с выбором роли: рекрутер, эксперт, менеджер, кандидат №1–3.

### Key Entities

- **Vacancy** — название, грейд, статус, версии рубрики и комплекта, эксперт, менеджер.
- **Candidate / Interview** — имя, токен ссылки, состояние интервью, дедлайн, язык, senior-режим.
- **Requirement** — обязательность, статус, вопрос, цитата, причина статуса.
- **Question** — номер, тип, лимиты, формулировки, правило уточнения.
- **Decision** — решение рекрутера, автор, дата, комментарий; история не удаляется.
- **ProctoringEvent** — тип, время, длительность; не входит в оценку.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Демо-путь C1 → C6/C7 → C9 → R3 → R5 → R6 → решение → M4 проходит без консоли и без бэкенда.
- **SC-002**: На любом экране MVP рекрутер за одну минуту понимает, что делать дальше, без процентов и без графика.
- **SC-003**: Кандидат на C1 за 15 секунд понимает длительность, число вопросов и дедлайн.
- **SC-004**: Жюри может открыть E2/E4 и увидеть, откуда взялась рубрика, не ломая демо-данные.
- **SC-005**: Каждый пилот-маршрут открывается и читается как макет, не как пустая 404.

## Assumptions

- Источник правды по текстам и раскладке экранов — спецификация из чата, не архитектурный документ live-контура.
- Визуальный язык — Napoleon: почти монохром, кобальт, квадратные скобки, токены из `tokens.css`.
- Данные хранятся локально в браузере / в памяти демо-модуля.
- Запись микрофона на демо может быть имитацией; если браузер даёт доступ, индикатор уровня звука желателен.
- Экраны C11 и A1–A4 не входят в поставку (метка «Позже»), кроме короткой заглушки C11.
- Тёмная тема поддерживается переключателем `data-theme`, как в прототипе.
