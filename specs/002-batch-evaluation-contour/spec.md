# Feature Specification: Batch-контур оценки кандидата

**Feature Branch**: `002-batch-evaluation-contour`

**Created**: 2026-09-03

**Status**: Partially implemented — правило вердикта готово, воркер целиком нет (см. «Синхронизация с кодом»)

**Input**: `docs/Архитектура и дизайн MVP.md`, разделы 2.4, 5, 5.1, 3; `evaluation-agent/README.md`

## Синхронизация с кодом

Реализовано (`evaluation-agent/src/evaluation_agent/`):
- `verdict.py` — правило вынесения вердикта (раздел 5.1 архитектурного документа) реализовано полностью, `pytest` — 11/11, каждый тест называет конкретный пункт правила.
- `schema.py` — типы, независимая копия от `Evaluation`/`Question`, сервисы не шарят ORM.

Не реализовано (`worker.py` — каркас, `NotImplementedError` на запуске):
- Точный ASR по завершённому интервью.
- Нарезка записи по таймстампам.
- LLM-оценка по вопросам (генерация `skill_scores[]`/`quotes[]`/`confidence` на вопрос).
- Запись результата в backend.
- Потребление очереди (Redis, в зависимостях, не подключено) вместо чтения файлов — сервис реагирует на `interview_completed` из протокола [[001-live-interview-contour]].

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вердикт по кандидату считается по явной формуле, а не «на глазок» (Priority: P1)

По собранным `skill_scores[]` система выносит один из трёх вердиктов: подходит / не
подходит / требуется доп. проверка — по приоритету сверху вниз (раздел 5.1).

**Why this priority**: это самая рискованная часть продукта (H1 в бэклоге) — без явной
воспроизводимой формулы оценщик каждый раз будет изобретать логику заново.

**Independent Test**: `pytest evaluation-agent/tests/test_verdict.py` — уже проходит,
11/11, без внешней инфраструктуры.

**Acceptance Scenarios**:

1. **Given** хотя бы один обязательный навык имеет `score < 40` (`fail`), **When** считается вердикт, **Then** результат — «не подходит», независимо от остальных навыков (реализовано).
2. **Given** `contradictions_found` не пуст, **When** считается вердикт, **Then** результат не может быть «подходит» — минимум «требуется доп. проверка» (реализовано).
3. **Given** обязательный навык `ambiguous` (40–59) или `untested` (ни одного `baseline`-вопроса), **When** считается вердикт и явных `fail`/противоречий нет, **Then** результат — «требуется доп. проверка» (реализовано).
4. **Given** `stretch`-вопрос по обязательному навыку провален, **When** считается минимум по навыку, **Then** этот провал не тянет навык в `fail` — только `baseline`-вопросы участвуют в минимуме (реализовано, тест на «stretch-бонус не топит навык»).
5. **Given** ответ помечен `answered_with_hint=true`, **When** считается score для агрегации, **Then** используется `min(score, 60)` (реализовано).

---

### User Story 2 - Асинхронная обработка интервью от записи до отчёта (Priority: P1)

После `interview_completed` воркер прогоняет точный ASR, оценивает каждый ответ по
рубрике LLM-вызовом, агрегирует в `Evaluation` и пишет результат в backend, чтобы
рекрутёр увидел готовый отчёт в [[003-recruiter-vacancy-management]].

**Why this priority**: без этого шага `verdict.py` считает вердикт только в тестах —
продукт не может показать реальный отчёт ни одному рекрутёру.

**Independent Test**: пока не тестируемо end-to-end — `worker.py` бросает
`NotImplementedError` при запуске. План по шагам — докстринг `run_worker()` в файле.

**Acceptance Scenarios**:

1. **Given** live-контур записал протокол `out/<interview_id>.jsonl`, **When** воркер получает сигнал `interview_completed`, **Then** запускается точный ASR по видео/аудио каждого ответа. *(не реализовано)*
2. **Given** транскрипт готов, **When** оценивается каждый вопрос, **Then** LLM-вызов возвращает `skill_scores[]`, `quotes[]`, `confidence` в формате, совместимом с `verdict.py`. *(не реализовано)*
3. **Given** оценка по всем вопросам собрана, **When** вызывается `compute_verdict` (или эквивалент из `verdict.py`), **Then** результат записывается в backend как `Evaluation`, статус интервью меняется на «готово». *(не реализовано — зависит от [[003-recruiter-vacancy-management]], у backend пока нет доменной модели `Evaluation`)*

### Edge Cases

- Live-контур недоступен/отвечает с задержкой — открытый вопрос (раздел 10 архитектурного документа), не решён ни здесь, ни в коде.
- Точный ASR медленнее ожидаемого (та же `large-v3-turbo`, что оказалась слишком медленной для live-контура на CPU без GPU — здесь это допустимо, но нужно замерить реальное время обработки).
- Очередь (Redis) сейчас не подключена — сервис не может по-настоящему реагировать на события, только читать файлы вручную/по скрипту.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST вычислять `score` (0–100) для каждого `skill_tag` вопроса по фиксированным якорям шкалы (раздел 5.1) — реализовано в `verdict.py` как принимаемый вход, генерация самого score из транскрипта не реализована.
- **FR-002**: Система MUST агрегировать обязательные навыки минимумом по `baseline`-вопросам, дополнительные — средним (реализовано в `verdict.py`).
- **FR-003**: Система MUST выносить вердикт по приоритету: `fail` обязательного навыка → «не подходит»; иначе противоречие → «требуется доп. проверка»; иначе `ambiguous`/`untested` обязательного навыка → «требуется доп. проверка»; иначе «подходит» (реализовано).
- **FR-004**: Система MUST версионировать промпт и модель на каждый вердикт (`model_version`, `prompt_version` — раздел 5, п.7) — поле есть в `schema.py`, фактическая генерация вердикта из LLM-вызова не реализована, версии не проставляются в рантайме.
- **FR-005**: Система MUST генерировать `summary_intro`/`summary_conclusion` тем же батч-пайплайном, без противоречия посчитанному `verdict` (раздел 2.4, п.3) — **не реализовано**.
- **FR-006**: Система MUST не переиспользовать черновой ASR live-контура для финальной оценки — только точный ASR батч-контура (раздел 3) — **не реализовано** (ASR-шаг воркера отсутствует).

### Key Entities

- **Evaluation** — см. модель данных в архитектурном документе, раздел 4: `per_question[]`, `overall_score`, `verdict`, `confirmed_skills[]`/`unconfirmed_skills[]`, `contradictions_found[]`, `summary_intro`/`summary_conclusion`.
- **VerdictInput** (рабочее имя в `verdict.py`) — независимая от backend Pydantic-схема входа в правило вердикта.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `pytest evaluation-agent/tests -q` — 11/11 зелёных (уже выполняется).
- **SC-002**: `python -m evaluation_agent.worker` обрабатывает хотя бы один реальный `out/<interview_id>.jsonl` от live-контура до записи `Evaluation` в backend без `NotImplementedError` — не достигнуто, это следующий крупный кусок работы проекта.
- **SC-003**: Время от `interview_completed` до готового отчёта — цель зафиксировать после первого рабочего прогона воркера (сейчас нет данных для оценки).

## Assumptions

- `evaluation-agent` остаётся отдельным сервисом с собственной копией типов, не шарит ORM с `backend/` — уже принятое решение, не пересматривается в рамках этого спека.
- Переход с чтения файлов протокола на потребление очереди (Redis) — часть той же фичи, не отдельный спек, так как это транспорт, а не изменение бизнес-логики.
- Реализация `worker.py` зависит от появления соответствующих моделей (`Interview`, `Evaluation`) в backend — см. [[003-recruiter-vacancy-management]]; до этого воркер можно развивать и тестировать только на моках.
