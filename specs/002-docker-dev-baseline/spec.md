# Feature Specification: Docker Dev Baseline

**Feature Branch**: `[002-docker-dev-baseline]`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "Сделать локальный dev startup baseline: FE и BE должны запускаться через докер. frontend должен быть настроен на работу с backend, AI-сервисы и evaluation-agent временно исключены из happy path локального запуска. не забудь создать .env файлы для проектов чтоб переменные не были захардкожены"

## Clarifications

### Session 2026-09-03

- Q: Должен ли baseline зависеть от общего runtime-артефакта для frontend и backend? → A: Нет, frontend и backend должны стартовать из раздельных Docker-артефактов, чтобы их можно было переиспользовать в CI и разворачивать независимо.
- Q: Должен ли baseline требовать ручного добора dependency tooling вне проектов перед сборкой образов? → A: Нет, каждый core-сервис должен хранить полный набор dependency metadata и build tooling в своём проекте, чтобы его образ собирался одинаково локально и в CI без переписывания setup.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start core app locally (Priority: P1)

Как разработчик, я хочу поднять frontend и backend в локальной среде через единый docker-based happy path, чтобы быстро получить рабочую базовую среду без ручной настройки процессов на хост-машине.

**Why this priority**: Без воспроизводимого локального старта невозможно безопасно продолжать разработку и проверять изменения в двух основных приложениях.

**Independent Test**: На чистой машине разработчик выполняет documented startup flow и получает доступный frontend и доступный backend без ручного запуска отдельных dev-команд вне контейнеров.

**Acceptance Scenarios**:

1. **Given** разработчик находится в корне репозитория и заполнил локальные переменные окружения, **When** он выполняет baseline startup flow, **Then** frontend и backend запускаются и остаются доступными одновременно.
2. **Given** baseline startup flow завершился, **When** разработчик открывает пользовательский интерфейс и endpoint проверки состояния backend, **Then** оба сервиса отвечают успешно.
3. **Given** frontend и backend нужны в разных окружениях, **When** команда использует runtime-артефакты за пределами локальной машины, **Then** каждый core-сервис может быть собран, запущен и переиспользован независимо от другого.

---

### User Story 2 - Use frontend against local backend by default (Priority: P2)

Как разработчик, я хочу чтобы frontend по умолчанию обращался к локальному backend из того же dev baseline, чтобы не перенастраивать адреса сервисов вручную перед каждой проверкой UI.

**Why this priority**: Локальный запуск теряет ценность, если frontend остаётся изолированным или требует ручной правки конфигурации для связи с backend.

**Independent Test**: После старта baseline frontend использует локальный backend endpoint из окружения по умолчанию и не требует изменения исходного кода для первичной интеграционной проверки.

**Acceptance Scenarios**:

1. **Given** frontend и backend запущены в baseline-конфигурации, **When** frontend выполняет запрос к backend, **Then** запрос направляется в локальный backend экземпляр, а не во внешний сервис.
2. **Given** backend временно недоступен, **When** frontend пытается обратиться к backend, **Then** причина недоступности видна разработчику без необходимости исследовать исходный код или искать захардкоженный адрес.

---

### User Story 3 - Keep local configuration out of code (Priority: P3)

Как разработчик, я хочу хранить локальные переменные запуска в `.env` файлах проектов, чтобы baseline не зависел от захардкоженных значений и был проще для сопровождения.

**Why this priority**: Управляемая конфигурация уменьшает вероятность случайных расхождений между окружениями и упрощает адаптацию baseline под другие машины.

**Independent Test**: Разработчик может изменить локальные значения конфигурации через `.env` файлы без редактирования исходного кода и без нарушения baseline startup flow.

**Acceptance Scenarios**:

1. **Given** проект клонирован заново, **When** разработчик создаёт локальные `.env` файлы по ожидаемому шаблону, **Then** baseline startup flow использует эти значения автоматически.
2. **Given** локальный адрес одного из core-сервисов изменён в `.env`, **When** baseline перезапускается, **Then** обновлённая конфигурация применяется без правки кода.

---

### Edge Cases

- Что происходит, если локальные `.env` файлы отсутствуют или неполны при первом запуске.
- Что происходит, если frontend стартует раньше backend и первое обращение к backend временно неуспешно.
- Что происходит, если разработчик случайно запускает более широкий compose flow, включающий AI-сервисы или evaluation-agent.
- Что происходит, если локальный порт frontend или backend уже занят другим процессом.
- Что происходит, если для CI или отдельного хостинга требуется поднять только frontend или только backend без второго core-сервиса.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять один documented локальный startup baseline для совместного запуска frontend и backend через Docker.
- **FR-002**: Система MUST гарантировать, что happy path локального запуска включает frontend и backend как обязательные core-сервисы.
- **FR-003**: Система MUST исключать AI-сервисы и evaluation-agent из happy path локального запуска, чтобы их состояние не блокировало базовый dev startup.
- **FR-004**: Система MUST позволять frontend обращаться к локальному backend экземпляру по конфигурации по умолчанию без ручной правки исходного кода.
- **FR-005**: Система MUST хранить изменяемые адреса сервисов и иные локальные runtime-параметры вне исходного кода, в `.env` файлах соответствующих проектов.
- **FR-006**: Система MUST предоставлять ожидаемый способ создания или получения локальных `.env` файлов для frontend и backend при первом запуске.
- **FR-007**: Система MUST делать источник конфигурации для frontend и backend прозрачным для разработчика, чтобы можно было понять, какие значения используются локально.
- **FR-008**: Система MUST позволять independently перезапускать baseline после изменения локальных переменных окружения без дополнительных ручных шагов в коде.
- **FR-009**: Система MUST явно отделять baseline startup flow от более широких локальных сценариев, которые включают дополнительные сервисы вне core happy path.
- **FR-010**: Система MUST описывать минимальную проверку успешного baseline-запуска, подтверждающую доступность frontend и backend после старта.
- **FR-011**: Система MUST сохранять раздельные runtime-артефакты для frontend и backend, чтобы каждый core-сервис можно было собирать, запускать и поставлять независимо.
- **FR-012**: Система MUST обеспечивать, что локальный baseline использует те же отдельные runtime-артефакты, которые могут быть переиспользованы в CI и в сценариях раздельного хостинга сервисов.
- **FR-013**: Система MUST не требовать объединения frontend и backend в один неделимый runtime-образ или один обязательный deployment unit для успешного baseline и последующего переиспользования.
- **FR-014**: Система MUST хранить для каждого core-сервиса полный и актуальный набор dependency metadata и build tooling внутри соответствующего проекта, чтобы runtime-артефакт можно было воспроизводимо собирать в локальной среде и CI без ручной адаптации окружения.

### Key Entities *(include if feature involves data)*

- **Local Dev Baseline**: Определённый локальный сценарий запуска, который описывает обязательные core-сервисы, ожидаемую команду старта и результат успешного запуска.
- **Project Environment File**: Локальный набор переменных окружения для конкретного проекта, содержащий изменяемые runtime-настройки без захардкоженных значений в коде.
- **Core Service Connection**: Ожидаемая связь между frontend и backend в локальном запуске, включая адрес назначения и поведение при недоступности backend.
- **Core Runtime Artifact**: Самостоятельный runtime-пакет для одного core-сервиса, пригодный для локального старта, CI-переиспользования и независимого развертывания.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Новый разработчик может запустить локальный baseline и открыть frontend вместе с backend не более чем за 15 минут, следуя только репозиторным инструкциям.
- **SC-002**: В 100% проверок по documented happy path frontend и backend одновременно становятся доступными после baseline startup flow.
- **SC-003**: Не менее 90% первичных локальных проверок UI, требующих backend, выполняются без ручной смены адресов сервисов или редактирования исходного кода.
- **SC-004**: Дополнительные AI-сервисы и evaluation-agent не требуются для успешного прохождения базовой проверки локального запуска frontend и backend.
- **SC-005**: Команда может использовать отдельный runtime-артефакт frontend или backend в изолированной проверке или отдельном окружении без обязательной пересборки второго core-сервиса.

## Assumptions

- Baseline ограничен локальной разработкой для `frontend/` и `backend/` и не обязан покрывать остальные сервисы репозитория.
- Для первого этапа достаточно happy path, в котором разработчик поднимает только core-сервисы, а расширенные сценарии запуска документируются отдельно.
- `.env.example` или эквивалентные шаблоны уже рассматриваются как допустимая основа для создания локальных `.env` файлов.
- Проверка успешного запуска может опираться на доступность пользовательского интерфейса frontend и проверочного endpoint backend.
- Повторное использование в CI и потенциальный раздельный хостинг считаются обязательными целями baseline, а не вторичными улучшениями.
- Для каждого core-сервиса источником истины для сборки считаются его собственные dependency declarations и lockfiles, а не внешние ручные инструкции на машине разработчика.
