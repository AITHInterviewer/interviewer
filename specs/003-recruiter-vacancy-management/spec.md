## User Scenarios & Testing *(mandatory)*

### User Story 1 - Рекрутёр создаёт вакансию и получает сгенерированные вопросы (Priority: P1)

Рекрутёр заполняет форму вакансии (название, описание, грейд, обязательные/дополнительные
навыки), получает LLM-сгенерированный список базовых вопросов с `skill_tag`/`intent`/
`reference_answer`/`estimated_duration_sec`, может править, удалять, добавлять вопросы и
менять их порядок; видит живой пересчёт ожидаемой длительности интервью.

**Why this priority**: без вопросов с эталонными ответами весь батч-контур ([[002-batch-evaluation-contour]]) не имеет входа — это корень модели данных всего продукта.

**Independent Test**: создать вакансию через API/UI с одним обязательным навыком, получить
непустой список вопросов, в каждом из которых заполнены `skill_tag`, `intent`,
`reference_answer`.

**Acceptance Scenarios**:

1. **Given** рекрутёр заполнил форму вакансии и нажал «сгенерировать вопросы», **When** генерация завершена, **Then** список вопросов содержит `skill_tag[]`, `intent`, `reference_answer`, `estimated_duration_sec` для каждого вопроса (раздел 2.1, п.2).
2. **Given** рекрутёр редактирует вопрос вручную (текст/skill_tag/эталон), **When** сохраняет форму, **Then** правки сохраняются без потери остальных полей (раздел 2.1, п.3).
3. **Given** рекрутёр добавляет ручной вопрос, **When** не указывает `skill_tag`/`intent`/эталон сам, **Then** система предлагает сгенерировать их по тексту вопроса (раздел 2.1, п.3).
4. **Given** сумма верхних границ длительности вопросов превышает ~40–45 минут, **When** рекрутёр находится в редакторе вопросов, **Then** показывается мягкое предупреждение, не блокирующее сохранение (раздел 2.1.2).
5. **Given** список вопросов сохранён, **When** рекрутёр нажимает «Сохранить», **Then** вакансия переходит в статус `ready` (раздел 2.1, п.4).

---

### User Story 2 - Рекрутёр создаёт интервью и получает ссылку для кандидата (Priority: P1)

На странице готовой вакансии рекрутёр загружает резюме кандидата (файл), опционально —
имя/контакт, и получает персональную ссылку на интервью.

**Why this priority**: это единственный способ запустить [[004-candidate-interview-flow]] — без ссылки кандидат не может начать интервью.

**Independent Test**: создать интервью по существующей вакансии с загруженным файлом
резюме, получить уникальный `access_token`, убедиться что он не предсказуем и не повторяется.

**Acceptance Scenarios**:

1. **Given** вакансия в статусе `ready`, **When** рекрутёр загружает резюме и создаёт интервью, **Then** создаётся запись `Interview` с уникальной непредсказуемой ссылкой по токену (раздел 2.2, п.2–3).
2. **Given** интервью создано, **When** рекрутёр открывает страницу вакансии, **Then** ссылку можно скопировать для ручной отправки (интеграций почты нет, раздел 2.2, п.4).

---

### User Story 3 - Рекрутёр видит таблицу кандидатов и открывает полный отчёт (Priority: P1)

Сравнительная таблица по вакансии: имя, дата прохождения, статус обработки, итоговая
рекомендация, общий балл. Клик по строке открывает карточку кандидата.

**Why this priority**: это единственная точка, где рекрутёр реально принимает решение —
без неё вся оценка ([[002-batch-evaluation-contour]]) никому не видна.

**Independent Test**: с моком готовой `Evaluation` для одного интервью — убедиться, что
таблица показывает строку с корректным статусом и вердиктом, а переход в отчёт открывает
все требуемые разделом 2.4 поля.

**Acceptance Scenarios**:

1. **Given** несколько интервью по вакансии в разных статусах обработки, **When** рекрутёр открывает список кандидатов, **Then** таблица показывает статус каждого («в обработке» / «готово») и не падает на «в обработке» записях без `Evaluation` (раздел 2.5, раздел 3).
2. **Given** интервью обработано, **When** рекрутёр открывает карточку кандидата, **Then** видно: вступление, оценка по навыкам, общий балл, вердикт с обоснованием и цитатами, заключение, ответ на вступительный вопрос и вопрос кандидата из финального приглашения (раздел 2.4).
3. **Given** рекрутёр открыл карточку кандидата, **When** он выставляет решение вручную, **Then** `RecruiterDecision` сохраняется отдельно от `Evaluation.verdict` (раздел 6 — юридическое требование, решение принимает человек).

### Edge Cases

- Резюме в неподдерживаемом формате/битый файл — не описано, требует уточнения при `speckit-clarify`.
- Вакансия с нулевым списком обязательных навыков — генерация вопросов на пустом входе.
- Повторное открытие ссылки на уже пройденное интервью — открытый вопрос (раздел 10 архитектурного документа: «одноразовая ссылка или можно возвращаться»), НЕ решён.
- Многотенантность (`Organization`) сознательно не закладывается — см. раздел 4 архитектурного документа и открытый вопрос о модели поставки (раздел 10).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Backend MUST предоставлять CRUD для `Vacancy` с полями из раздела 4 архитектурного документа (`title, description, grade, required_skills[], nice_to_have_skills[], status`).
- **FR-002**: Backend MUST генерировать список `Question` для вакансии LLM-вызовом, включая обязательные поля `skill_tag[]`, `intent`, `reference_answer`, `estimated_duration_sec`, `format` (раздел 2.1, 2.1.1, 2.1.2).
- **FR-003**: Backend MUST разрешать редактирование/добавление/удаление/переупорядочивание вопросов вакансии до сохранения статуса `ready`.
- **FR-004**: Backend MUST создавать `Interview` с непредсказуемым `access_token` и хранить `resume_file_url` в объектном хранилище (раздел 2.2, раздел 4).
- **FR-005**: Backend MUST отдавать таблицу интервью по вакансии со статусом обработки и (когда есть) итоговым вердиктом/баллом (раздел 2.5).
- **FR-006**: Backend MUST отдавать полный отчёт по интервью (`Evaluation` + связанные поля) для карточки кандидата (раздел 2.4).
- **FR-007**: Backend MUST хранить `RecruiterDecision` как отдельную сущность от `Evaluation.verdict`, требовать явного выставления рекрутёром (раздел 6).
- **FR-008**: Frontend MUST реализовать экраны: форма вакансии + редактор вопросов, создание интервью, список кандидатов, карточка отчёта (раздел 2.1–2.5).
- **FR-009**: Авторизация рекрутёра MUST быть логин/пароль или magic-link — без сложной ролевой модели (раздел 1).

### Key Entities

См. раздел 4 архитектурного документа как источник истины по полям: `Recruiter`,
`Vacancy`, `Question`, `Interview`, `Evaluation`, `RecruiterDecision`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Рекрутёр проходит путь «создал вакансию → получил вопросы → создал интервью → получил ссылку» без ручного вмешательства в БД, end-to-end через UI.
- **SC-002**: Таблица кандидатов и карточка отчёта корректно отображают мок/реальную `Evaluation`, включая все поля раздела 2.4.
- **SC-003**: Ни один экран не требует прямого похода в БД/консоль для демонстрации сценария рекрутёра.

## Assumptions

- Роль нанимающего менеджера не делается в этой итерации (раздел 1) — рекрутёр видит всё сам.
- Многотенантность не закладывается в схему — см. раздел 4, открытый вопрос модели поставки (раздел 10).
- Пока [[002-batch-evaluation-contour]] не производит реальные `Evaluation`, экраны рекрутёра можно и нужно разрабатывать и демонстрировать на замоканных данных отчёта.
