# Промт для Grok: доделать UX по обзору экранов

Скопируй всё, что ниже разделителя, в Grok с подключённой папкой `hakaton`.

---

Ты работаешь в репозитории `hakaton`, ветка `feat/ui-on-main`. Фронт в `frontend/`:
Next.js 16, React 19, TypeScript, Tailwind v4, компоненты shadcn в `components/shadcn`,
собственные атомы в `components/ui`, иконки Phosphor.

Открой `docs/ui-review/screens.html` в браузере. Это обзор 29 экранов: под каждым подпись,
зелёным отмечено сделанное, жёлтым — оставшееся. В конце страницы раздел «Как доделать
остальное». Твоя задача — закрыть двенадцать жёлтых пунктов из блока «Делается на фронте,
бэкенд не нужен». Три пункта из блока «Упирается в бэкенд» не трогай.

## Правила, которые нельзя нарушать

Канон продукта лежит в `docs/artifacts/00-canon/PRODUCT.md`, коротко:

- Никаких процентов и общего балла. Статусы словами.
- Система предлагает, человек решает. Эти сущности разделены визуально.
- Действие, которое ничего не меняет, либо выключено с причиной рядом, либо честно помечено.
  Кнопка не показывает успех, которого нет.
- «Недостаточно данных» всегда объясняет причину и следующий шаг.

Дизайн-система живёт в `frontend/app/globals.css`:

- Шесть кеглей и ничего между ними: 34/600, 18/600, 16/400, 14/400, 14 mono, 12/600 логотип.
  Текста мельче 14px не бывает.
- Один акцент `#140af0`. Зелёный, жёлтый, красный — статусы, не второй бренд.
- Кнопка 38px, крупная 42px, поле 42px, радиусы 8 / 12 / 999.
- Моноширинный только на версии, таймкоды и токены.
- Готовые атомы: `Button` (умеет `loading` со спиннером и `aria-busy`), `StatusPill`,
  `Skeleton`, `Modal` с ловушкой фокуса, `SearchField`, `SelectField`, `Toolbar`, `Tag`.
  Сначала проверь, есть ли нужное, потом пиши своё.

## Что сделать

Пункты в порядке, в котором их стоит брать. Каждый — отдельный коммит.

1. **Дедлайны у кандидата.** На `/i/[token]`, `/i/[token]/done` и `/i/[token]/extra/[id]` не видно,
   до какой даты действовать. Прокинь срок из ответа API и покажи его строкой.
2. **Кнопка заметки.** На `/i/[token]/request` заметка сохраняется в браузере, а кнопка называется
   «Отправить». Переименуй в «Сохранить заметку», пока отправки на сервер нет.
3. **Подтверждение архива.** В `frontend/app/vacancies/[id]/settings/settings-client.tsx` вынеси
   «Пауза» и «Архив» из формы в блок «Жизненный цикл», архив оберни в `Modal` с подтверждением.
4. **Поиск и снятие роли у сотрудников.** `frontend/app/internal/users/page.tsx`: добавь
   `SearchField` и контрол снятия роли (в API уже есть `updateRoleAssignments`).
5. **Дубль колонок у менеджера.** В `frontend/app/manager/page.tsx` сведи «Доступ» и «Что сделать»
   в одну колонку: «Передан вам, нужна встреча» или «Спросили мнение».
6. **Требования в брифе.** В `frontend/app/brief/[id]/page.tsx` покажи `required_skills` вакансии:
   менеджер их формулировал, а видит только цифры.
7. **Контекст в списке аудитов.** В `frontend/app/audit/[vacancyId]/page.tsx` к имени кандидата
   добавь требование и причину запроса, они приходят в очереди эксперта.
8. **Что дальше после создания вакансии.** В `frontend/app/vacancies/new/page.tsx` под кнопкой
   напиши порядок: создаём, собираем вопросы, отправляем эксперту.
9. **Заголовок регистрации.** В `frontend/app/register/page.tsx` «Первый аккаунт рекрутера» врёт,
   когда аккаунты уже есть. Переименуй в «Регистрация рекрутера».
10. **Тупик на входе.** В `frontend/app/login/page.tsx` под ошибкой добавь строку, куда писать,
    если пароль не подошёл.
11. **Требования из калибровки.** На `/vacancies/[id]/rubric` требования правятся только через
    настройки вакансии. Повтори форму списка навыков здесь и дергай тот же `updateVacancy`.
12. **Очередь аудитов.** `/expert/queue` повторяет блок с главного экрана эксперта. Либо удали
    маршрут и оставь блок, либо добавь сюда фильтр «открытые / закрытые» и историю ответов.
    Выбери сам и напиши в отчёте, что выбрал и почему.

## Как проверять

Бэкенда под рукой нет, поэтому экраны снимаются с подменёнными ответами API:

```bash
cd frontend && npm run dev
cd tools/live-view && node mock-shots.mjs users=/internal/users manager=/manager
```

Скриншоты падают в `tools/live-view/out/`. Фикстуры и мок кандидата — в
`tools/live-view/fixtures.mjs`, правь их, если для проверки нужны другие данные.

После каждого пункта:

```bash
cd frontend && npm run lint && npx tsc --noEmit && npm test && npm run build
cd tools/live-view && node route-check.mjs
```

Все четыре команды должны быть чистыми, 57 тестов зелёными, обход маршрутов без проблем.
Если правишь текст, который проверяет тест, обнови тест: не отключай его.

## Границы

Не трогай: `backend/`, `live-agent/`, `evaluation-agent/`, `infra/`, папку `components/shadcn`
(это вендорный код, обновляется командой `shadcn add`).

Не добавляй: новые UI-библиотеки, второй набор иконок, второй акцентный цвет, тёмную тему
(её сняли намеренно, в системе одна светлая).

Не выдумывай данных: если поля нет в API, покажи честное пустое состояние, а не заглушку,
которая выглядит как настоящее значение.
