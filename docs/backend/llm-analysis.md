# Анализ интервью и генерация вопросов: что делаем на бэкенде

Дата: 6 сентября 2026. Ветка: `feat/ui-on-main`.

Документ описывает один слой: обращения к языковой модели и данные вокруг них. Классификаторы,
эмбеддинги и любой обучаемый код на Python сюда не входят — сначала работающие промты, потом,
если понадобится, всё остальное.

## 1. Что уже есть и чего нет

Проверено по коду, не по памяти.

**Есть:**

| Что | Где | Состояние |
|---|---|---|
| Модель `Interview` с полями `report_status` и `report_json` | `backend/app/models/interview.py:47-50` | поля объявлены, никто не пишет |
| Модель `Answer`: `transcript_text`, `started_at`, `completed_at`, `code_submission` | `backend/app/models/answer.py` | заполняется контуром интервью |
| Модель `Question`: `skill_tag[]`, `intent`, `reference_answer`, `difficulty`, `role` | `backend/app/models/question.py` | заполняется генерацией |
| Модель `RubricVersion.snapshot` (JSONB) | `backend/app/models/rubric_version.py:27` | слепок требований на момент утверждения |
| Генерация вопросов через Claude Agent SDK | `backend/app/services/vacancy_llm_service.py` | работает, но на подписке Claude |
| `GET /api/v1/interviews/{id}/events` — ответы и события | `backend/app/routers/interviews_admin.py:56` | отдаёт расшифровки |
| Каркас правила вердикта | `evaluation-agent/src/evaluation_agent/verdict.py` | считает баллы, в продукте не используется |

**Нет:**

- Ничего не пишет `report_json`, поэтому отчёт на фронте собирается на лету из требований
  вакансии и тегов вопросов (`frontend/lib/report.ts`). Это честный запасной вариант, но он
  не умеет главного: понять, ответил человек по существу или ушёл в сторону.
- Нет обращения к модели по ответам кандидата. Разбор ответа не делается вообще.
- Нет OpenRouter: в репозитории он не упоминается ни разу.
- Нет эндпоинта, который отдаёт отчёт, и нет ручки для исхода встречи у менеджера.

## 2. Провайдер и модель

Берём OpenRouter, модель `google/gemini-2.5-flash`. Причины: дёшево на объёме разборов,
держит русский, отдаёт строгий JSON по схеме, ключ уже есть.

Новые переменные окружения в `backend/app/config.py` (класс `Settings`):

```python
    # OpenRouter — анализ ответов и генерация вопросов.
    # Ключ не коммитим: берётся из окружения, в docker-compose пробрасывается из .env
    openrouter_api_key: str = ""
    openrouter_base_url: str = "https://openrouter.ai/api/v1"
    llm_model_analysis: str = "google/gemini-2.5-flash"
    llm_model_generation: str = "google/gemini-2.5-flash"
    llm_timeout_seconds: int = 60
    llm_max_retries: int = 2
    # OpenRouter просит эти два заголовка для учёта трафика
    openrouter_referer: str = "https://napoleon-interview.local"
    openrouter_title: str = "Napoleon Interview"
```

Ключ кладём в `backend/.env` строкой `OPENROUTER_API_KEY=...` и в `.gitignore` (проверить, что
`.env` там уже есть). В логи ключ не пишем никогда: при логировании запроса вырезаем заголовок
`Authorization`.

Если `openrouter_api_key` пуст, сервис не падает: он возвращает `LLMUnavailable`, а вызывающий
код ставит отчёту статус `processing` и пишет в лог предупреждение. Продукт должен работать без
ключа, просто без разбора.

## 3. Клиент

Новый файл `backend/app/services/llm_client.py`. Один класс, один метод, никаких абстракций
на будущее.

Требования к реализации:

1. `httpx.AsyncClient` с таймаутом из настроек, повтор при 429 и 5xx с паузой 1с и 4с,
   максимум `llm_max_retries` повторов. При 4xx кроме 429 повтор не делаем.
2. Запрос: `POST {base_url}/chat/completions`, тело — `model`, `messages`, `temperature`,
   `response_format`. Для всех наших вызовов `temperature: 0.2`: нам нужна повторяемость,
   а не разнообразие.
3. Строгий JSON. У OpenRouter это `response_format: {"type": "json_schema", "json_schema":
   {"name": "...", "strict": true, "schema": {...}}}`. Схему берём из Pydantic-модели через
   `model_json_schema()`, как это уже сделано в `vacancy_llm_service.py`.
4. Ответ валидируем Pydantic-моделью. Если валидация не прошла — один повтор с добавленным
   сообщением `Ответ не прошёл валидацию: <ошибка>. Верни только JSON по схеме.` Второй раз
   не пробуем, поднимаем `LLMInvalidResponse`.
5. Логируем: модель, число токенов из `usage`, длительность, идентификатор интервью. Тексты
   ответов кандидата в логи не пишем — это персональные данные.

```python
class LLMError(Exception): ...
class LLMUnavailable(LLMError): ...      # нет ключа или провайдер недоступен
class LLMInvalidResponse(LLMError): ...  # ответ не по схеме дважды подряд
```

## 4. Откуда берём данные

Для каждого обращения к модели собираем контекст из базы. Ничего не додумываем и не
подмешиваем данные других кандидатов.

**Генерация комплекта вопросов** (`vacancy_id`):

| Поле промта | Источник |
|---|---|
| Название, грейд, описание | `vacancy.title`, `vacancy.grade`, `vacancy.description` |
| Обязательные требования | `vacancy.required_skills` |
| Желательные требования | `vacancy.nice_to_have_skills` |

**Разбор одного ответа** (`answer_id`):

| Поле промта | Источник |
|---|---|
| Текст вопроса | `question.text` |
| Что проверяет вопрос | `question.intent` |
| Эталонный ответ | `question.reference_answer` |
| Требования вопроса | `question.skill_tag` |
| Сложность | `question.difficulty` |
| Расшифровка ответа | `answer.transcript_text` |
| Код, если есть | `answer.code_submission`, `answer.code_language` |
| Длительность ответа | `answer.completed_at - answer.started_at` |

Резюме кандидата (`interview.resume_file_url`) в разбор **не передаём**. Оценка идёт по ответу,
а не по бумаге: иначе модель начнёт достраивать то, чего человек не говорил.

**Сборка отчёта** (`interview_id`):

| Поле промта | Источник |
|---|---|
| Требования вакансии | `rubric_version.snapshot` если есть, иначе `vacancy.required_skills` |
| Разборы ответов | результаты шага 6, сложенные в `report_json.answers` |
| Что осталось без вопроса | считается кодом, не моделью: требования без пересечения со `skill_tag` |

Последнее важно. Покрытие требований вопросами — арифметика, её делает Python, не модель.
Модель отвечает только на вопрос «что видно в этом ответе».

## 5. Системный промт: комплект вопросов

Заменяет текущий промт в `vacancy_llm_service.py`. Модель та же на всех вызовах.

```
Ты помогаешь техническому эксперту собрать комплект вопросов для асинхронного технического
интервью. Интервью проходит без интервьюера: кандидат отвечает голосом, вопросы одинаковые
для всех, поэтому формулировка должна работать без уточнений вживую.

Правила:

1. Ровно шесть вопросов: один разогревающий (role="warmup"), четыре оценочных
   (role="assessment"), один завершающий (role="closing").
2. Каждый оценочный вопрос закрывает минимум одно требование вакансии. Тег в skill_tag
   пишется дословно так, как требование названо в вакансии, без синонимов и переводов.
   Если написано «SQL и индексы», в теге тоже «SQL и индексы».
3. Вместе четыре оценочных вопроса должны закрыть как можно больше обязательных требований.
   Если требований больше четырёх, выбирай те, где ответ голосом даст больше всего сигнала,
   и не пытайся втиснуть два разных требования в один вопрос ради покрытия.
4. Вопрос просит рассказать о своём опыте, а не пересказать определение. Плохо: «Что такое
   индекс в базе данных». Хорошо: «Запрос по заказам стал медленным. Как выясняете причину
   и что делаете с индексами».
5. intent — что именно проверяет вопрос, одной фразой, для эксперта, не для кандидата.
   reference_answer — признаки сильного ответа, чтобы человек мог сверить, а не оценка.
6. Разогревающий и завершающий вопросы оставь без intent, reference_answer и skill_tag.

Ограничения формы:

- Язык русский, обращение на вы.
- text: до 220 символов, одно-два предложения, без нумерации и маркеров в начале.
- intent: до 120 символов.
- reference_answer: до 240 символов.
- estimated_duration_sec: целое от 120 до 240.
- format: "voice" для всех вопросов.
- difficulty: смешивай "baseline" и "stretch", но stretch не больше двух.
- Не используй markdown, звёздочки, решётки, эмодзи и кавычки-ёлочки внутри text.
- Не пиши «пожалуйста», «расскажите, пожалуйста», «было бы здорово».

Верни только JSON по схеме, без пояснений до и после.
```

Схема ответа — уже существующая `GeneratedQuestionSet` из `vacancy_llm_service.py`.

## 6. Системный промт: разбор одного ответа

Новый сервис `backend/app/services/answer_analysis_service.py`. Вызывается на каждый ответ
роли `assessment` после того, как готова расшифровка.

```
Ты разбираешь один ответ кандидата на техническом интервью. Твоя работа — показать, что в
ответе есть и чего в нём нет, чтобы человек принял решение сам. Ты не выносишь вердикт,
не советуешь нанимать или отказать и не ставишь баллов.

Тебе дают вопрос, что он проверяет, признаки сильного ответа и расшифровку ответа кандидата.
Расшифровка автоматическая: в ней бывают оговорки, обрывы и ошибки распознавания. Не считай
их ошибками кандидата.

Определи одно из четырёх состояний по каждому требованию вопроса:

- "answered" — в ответе есть содержательный материал по требованию: свой опыт, конкретика,
  объяснение решения.
- "partial" — требование затронуто, но чего-то существенного не хватает: нет причины, нет
  проверки результата, нет личного вклада.
- "off_topic" — человек говорил, но не про это требование.
- "no_answer" — ответа нет: пусто, «не знаю», «пропущу».

Правила разбора:

1. Опирайся только на расшифровку. Если чего-то не сказано, значит этого нет, даже если по
   опыту кандидата это очевидно.
2. В observation пиши, что именно видно, своими словами, без оценочных ярлыков вроде
   «слабо», «плохо», «отлично», «джуновский уровень».
3. quote — дословный фрагмент расшифровки, который подтверждает вывод. Не сокращай слова
   внутри фрагмента, не переписывай его. Если подтверждения нет, оставь quote пустым.
4. missing — чего не хватило, одной фразой, только для состояний "partial" и "off_topic".
   Для "answered" и "no_answer" оставь пустым.
5. follow_up — какой один уточняющий вопрос закрыл бы пробел. Только для "partial" и
   "off_topic", иначе пусто.
6. Никаких чисел, процентов, оценок по шкале и слов «балл», «score», «уровень».

Ограничения формы:

- Язык русский. Обращение к читателю на вы, о кандидате в третьем лице.
- observation: одно-два предложения, до 240 символов.
- quote: до 400 символов, обрезай по границе предложения, многоточие не добавляй.
- missing и follow_up: до 120 символов каждое.
- Разделитель внутри строки — только « · » с пробелами. Тире, вертикальную черту и точку с
  запятой как разделители не используй.
- Никакого markdown: ни звёздочек, ни решёток, ни списков через дефис.
- Не начинай observation со слов «Кандидат» — это и так понятно, начни с сути.

Верни только JSON по схеме.
```

Схема:

```python
class RequirementFinding(BaseModel):
    skill_tag: str
    state: Literal["answered", "partial", "off_topic", "no_answer"]
    observation: str = Field(max_length=240)
    quote: str = Field(default="", max_length=400)
    missing: str = Field(default="", max_length=120)
    follow_up: str = Field(default="", max_length=120)

class AnswerAnalysis(BaseModel):
    findings: list[RequirementFinding]
```

`findings` содержит по элементу на каждый тег из `question.skill_tag`. Если модель вернула
меньше — дополняем недостающие состоянием `no_answer` и пустым observation, а в лог пишем
предупреждение. Если больше или тег не из вопроса — лишнее выбрасываем.

## 7. Системный промт: сводка отчёта

Вызывается один раз на интервью, после того как разобраны все ответы. На вход — уже готовые
findings, а не расшифровки: так дешевле и стабильнее.

```
Ты собираешь короткую сводку по итогам технического интервью для рекрутёра. Разборы
отдельных ответов уже сделаны, твоя работа — сложить их в три-четыре фразы и назвать
следующий шаг.

Правила:

1. Пиши только то, что следует из разборов. Не добавляй выводов о человеке, которых там нет.
2. Не выноси решение: не пиши «подходит», «не подходит», «рекомендуем». Решение принимает
   рекрутёр, и оно живёт отдельно.
3. Если по обязательному требованию нет ответа или он неполный, скажи об этом прямо и
   назови требование дословно.
4. next_step — один конкретный шаг: точечный доп. вопрос по конкретному требованию, разговор
   на встрече или ничего, если всё закрыто.
5. Никаких процентов, баллов и сравнений с другими кандидатами.

Ограничения формы:

- Язык русский, нейтральный тон.
- summary: до 320 символов, два-три предложения сплошным текстом, без списков.
- strengths и gaps: до пяти пунктов каждый, каждый пункт до 90 символов, без завершающей
  точки, без markdown-маркеров: это массив строк, маркеры нарисует интерфейс.
- next_step: до 120 символов, одно предложение.
- Разделитель внутри строки — только « · » с пробелами.
- Не используй markdown и эмодзи.

Верни только JSON по схеме.
```

Схема:

```python
class ReportSummary(BaseModel):
    summary: str = Field(max_length=320)
    strengths: list[str] = Field(default_factory=list, max_length=5)
    gaps: list[str] = Field(default_factory=list, max_length=5)
    next_step: str = Field(max_length=120)
```

## 8. Системный промт: догоняющий вопрос внутри сессии

Нужен для доспроса по покрытию: пока у кандидата есть время, дыру в обязательном требовании
закрываем в той же сессии, а не письмом после отчёта.

```
Ты формулируешь один короткий уточняющий вопрос кандидату прямо во время интервью. Его
задают, потому что по обязательному требованию не хватило материала.

Правила:

1. Один вопрос, без вводных, без «расскажите пожалуйста подробнее».
2. Опирайся на то, что человек уже сказал: начни с его же примера и попроси недостающую часть.
3. Не подсказывай ответ и не называй требование служебным термином из рубрики.
4. Вопрос должен закрываться ответом за минуту.

Ограничения формы:

- Язык русский, обращение на вы.
- До 180 символов, одно предложение, без markdown и без нумерации.

Верни только JSON по схеме.
```

Схема: `{"question": str}` с ограничением длины 180.

## 9. Контракт `report_json`

Это точка стыка с интерфейсом. Формат ниже фронт уже умеет читать: он совпадает по смыслу с
тем, что сейчас считается на клиенте в `frontend/lib/report.ts`, поэтому переход сведётся к
«если `report_json` пришёл, берём его, иначе считаем сами».

```json
{
  "version": 1,
  "generated_at": "2026-09-06T10:24:00Z",
  "model": "google/gemini-2.5-flash",
  "rubric_version_id": "uuid или null",
  "summary": {
    "summary": "Асинхронность и тестирование раскрыты на своих примерах · по очередям ответа нет",
    "strengths": ["Асинхронность: своё узкое место и способ проверки"],
    "gaps": ["Celery и очереди: ответа нет"],
    "next_step": "Точечный доп. вопрос по очередям или разговор на встрече"
  },
  "requirements": [
    {
      "skill": "Асинхронность",
      "mandatory": true,
      "coverage": "answered",
      "question_orders": [1],
      "findings": [
        {
          "question_id": "uuid",
          "question_order": 1,
          "state": "answered",
          "observation": "Называет узкое место и как измерила результат после перехода на asyncio",
          "quote": "Оказалось, что почти всё время он ждал внешние вызовы, а не считал",
          "missing": "",
          "follow_up": ""
        }
      ]
    },
    {
      "skill": "Celery и очереди",
      "mandatory": true,
      "coverage": "asked",
      "question_orders": [3],
      "findings": []
    },
    {
      "skill": "Code review",
      "mandatory": false,
      "coverage": "not-covered",
      "question_orders": [],
      "findings": []
    }
  ]
}
```

Правила заполнения:

- `coverage` считает Python, не модель: `answered` если хотя бы один finding в состоянии
  `answered` или `partial`; `asked` если вопрос есть, но ответа или расшифровки нет;
  `not-covered` если ни один вопрос не несёт этот тег.
- Порядок `requirements`: сначала обязательные в порядке из вакансии, потом желательные.
- `question_orders` — номера вопросов, как они видны кандидату и в комплекте.
- Никаких числовых оценок в JSON. Если в будущем появится шкала, она уедет в отдельное поле
  и в интерфейс не попадёт без отдельного решения.

## 10. Пайплайн и статусы

```
интервью сдано
      ↓
recompute_report(interview_id)   Celery-задача
      ↓
для каждого answer роли assessment без разбора → analyze_answer  (пункт 6)
      ↓
покрытие требований считается кодом  (пункт 9)
      ↓
build_summary по findings  (пункт 7)
      ↓
interview.report_json = {...}; interview.report_status = "ready"
```

Статусы `report_status` уже есть в модели: `processing`, `ready`, `updated_extra`,
`expert_reviewed`. Правила:

- Запуск задачи ставит `processing`.
- Успешная сборка ставит `ready`.
- Ответ на доп. вопрос запускает пересборку и ставит `updated_extra`.
- Отметка эксперта на аудите ставит `expert_reviewed` и отчёт не пересобирает.
- Любая ошибка модели оставляет прошлый `report_json` нетронутым и статус `processing`,
  с записью в лог. Пустой отчёт вместо старого не пишем.

Задачу вешаем на существующий Celery, файл `backend/app/tasks/interviews.py` сейчас пустой —
это его место. Идемпотентность: разбор ответа кэшируем по `answer_id` в таблице
`answer_analysis` (новая, поля `answer_id`, `findings JSONB`, `model`, `created_at`), чтобы
пересборка отчёта не платила за модель второй раз.

## 11. Эндпоинты, которых не хватает

| Метод и путь | Зачем | Кто зовёт |
|---|---|---|
| `GET /api/v1/interviews/{id}/report` | отдать `report_json` и `report_status` | экран отчёта у рекрутёра, карточка аудита у эксперта |
| `POST /api/v1/interviews/{id}/report/recompute` | пересобрать вручную | рекрутёр после доп. ответа |
| `POST /api/v1/manager/candidates/{id}/outcome` | исход встречи: «берём», «ещё этап», «нет» плюс комментарий | карточка встречи у менеджера |
| `GET /api/v1/vacancies/{id}/coverage` | покрытие требований вопросами | экран требований у эксперта |

Первые два закрывают отчёт. Третий — единственная роль, которая сейчас вообще ничего не может
записать в продукте: у менеджера есть экран, но нет ручки. Четвёртый необязателен: фронт уже
считает покрытие сам, но на сервере это надёжнее.

Доступы: отчёт видят рекрутёр вакансии и эксперт, назначенный на аудит. Менеджер видит только
то, что ему передали, и только по своей ручке.

## 12. Проверка длин и разделителей

Интерфейс не резиновый. После первой генерации отчёта обязательно посмотреть глазами, а не
только глазами тестов.

Куда какое поле попадает:

| Поле | Место в интерфейсе | Что ломается при переборе |
|---|---|---|
| `summary.summary` | абзац под заголовком «Что видно из ответов» | больше 320 символов — блок вытесняет карту требований ниже сгиба |
| `summary.strengths[]`, `gaps[]` | строки в сводке | длиннее 90 символов — перенос на две строки, колонка едет |
| `summary.next_step` | жёлтая строка «без ответа осталось обязательное» | длиннее 120 — строка занимает три ряда |
| `requirements[].skill` | заголовок строки карты требований | длиннее 40 символов — налезает на пилюлю статуса |
| `findings[].observation` | правая колонка карты требований | длиннее 240 — карточка растёт, детали уходят из вида |
| `findings[].quote` | цитата в рамке | длиннее 400 — вертикальная простыня, теряется смысл |

Проверить руками на реальном ответе:

1. Поднять бэкенд и фронт, открыть `/vacancies/{id}/candidates/{interview_id}`.
2. Убедиться, что карта требований показывает состояние по каждому требованию, а деталь
   справа — вопрос, цитату и строку «Эксперт ждал».
3. Проверить, что в тексте нет: markdown-звёздочек, решёток, эмодзи, слов «балл», «score»,
   «%», «уровень», «рекомендую».
4. Проверить разделители: внутри строки только « · ». Если модель вернула « — » или « | »,
   поправить промт, а не резать на фронте.
5. Взять кандидата, который ответил односложно, и убедиться, что отчёт не выдумал за него
   содержания: пустой ответ должен дать `no_answer` и пустую цитату.
6. Отключить `OPENROUTER_API_KEY` и убедиться, что экран отчёта не падает, а показывает
   «отчёт готовится».

Автоматически имеет смысл проверять то же самое в тестах: длины полей проверяет Pydantic,
а на запрещённые подстроки написать один тест, который прогоняет `report_json` через набор
регулярок (`%`, `**`, `##`, эмодзи, «балл»).

## 13. Тесты

Минимум, без которого не мержим:

1. `test_llm_client.py` — повтор на 429, отказ на 400, `LLMUnavailable` при пустом ключе.
   Провайдер замокан, сеть не трогаем.
2. `test_answer_analysis.py` — на замоканном ответе модели: findings дополняются до полного
   набора тегов, лишние теги выбрасываются, длины режутся.
3. `test_report_build.py` — покрытие считается кодом: требование без вопроса даёт
   `not-covered`, вопрос без расшифровки даёт `asked`, ответ даёт `answered`.
4. `test_report_api.py` — `GET /report` отдаёт 404 до сборки, 200 после, и не отдаёт отчёт
   чужому рекрутёру.
5. Тест на запрещённые подстроки из пункта 12.

## 14. Чего сейчас не делаем

- Классификаторов, эмбеддингов и обучаемых моделей на Python. Сначала промты и данные.
- Числовых баллов и общего скора. Их нет в продукте по канону, и добавлять их «во внутреннее
  поле» тоже не надо: поле всегда однажды вылезает в интерфейс.
- Автоматических решений: ни отказа, ни передачи менеджеру без человека.
- Разбора видео и прокторинга: прокторинг живёт отдельно и на технический вывод не влияет.
