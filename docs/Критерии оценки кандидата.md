# Критерии оценки кандидата

Практический референс по тому, как и из чего складывается оценка кандидата — извлечён
из [Архитектура и дизайн MVP.md](Архитектура%20и%20дизайн%20MVP.md) (разделы 4, 5, 5.1) и
сверен с уже реализованным кодом (`evaluation-agent/src/evaluation_agent/verdict.py`,
`schema.py` — единственная часть batch-контура, которая реально работает и покрыта
тестами, `evaluation-agent/tests/test_verdict.py`, 11/11 зелёных). Где документ и код
совпадают — ссылаюсь на код как источник истины; где документ описывает то, что ещё не
реализовано (сама оценка ответа LLM-судьёй, генерация вопросов) — явно помечено.

Адресат: тот, кто пишет промпт генерации вопросов (`backend`, спека
[[003-recruiter-vacancy-management]], `question_generation.py`) или промпт LLM-оценщика
ответов (`evaluation-agent`, ещё не реализован, см. `worker.py`) — обеим сторонам нужно
одно и то же понимание, что такое «данные, достаточные для оценки».

## 1. Из чего физически складывается оценка

Оценка не одно число — это трёхуровневая пирамида:

```
Question (эталон + тег навыка)
   │
   ▼
Answer → QuestionScore (по каждому skill_tag вопроса отдельно)
   │
   ▼ группировка по skill_tag
SkillVerdict (per navyk: fail / ambiguous / pass / untested)
   │
   ▼ приоритетное правило
Verdict (fits / not_fits / needs_review)
```

Реализовано (код): `SkillVerdict`-агрегация и финальный `Verdict` — `verdict.py`.
Не реализовано: генерация `QuestionScore` самим LLM-оценщиком ответа (это `worker.py`,
`NotImplementedError`) — но то, ЧТО он должен вернуть на выходе, зафиксировано схемой
(`QuestionScore` в `schema.py`) и это и есть контракт для будущего промпта LLM-судьи.

## 2. Что обязано быть в каждом вопросе, чтобы его вообще можно было оценить

Раздел 5, п.1 архитектурного документа: это не рекомендация, а жёсткое требование —
вопрос без этого триплета **не попадает в оценку**.

| Поле | Обязательность | Зачем именно это |
|---|---|---|
| `skill_tag[]` | Обязателен для `role=assessment` | Ключ агрегации — без тега ответ никуда не группируется. Массив, не строка — один вопрос может закрывать несколько навыков сразу (типично для `live_coding`, например `[Python, Алгоритмы]`) |
| `reference_answer` | Обязателен для `role=assessment` | Без эталона нечего сравнивать с ответом кандидата — `score` считается именно как «насколько ответ соответствует `reference_answer`» (раздел 5.1), не абстрактная оценка «умный ли ответ» |
| `intent` | Обязателен для `role=assessment` | Не участвует в самом расчёте `score`, но обязателен для читаемости отчёта (раздел 5, п.8) — рекрутёр должен видеть, зачем агент задал именно этот вопрос |
| `difficulty` (`baseline`/`stretch`) | Обязателен, default `baseline` | Определяет, участвует ли вопрос в **минимуме** по обязательному навыку (только `baseline`) или только даёт бонус (`stretch`) |
| `format` | Обязателен, default `voice` | Меняет, что именно сравнивается с `reference_answer` — текст ответа (`voice`/`code_review_verbal`) или код+рассуждение (`live_coding`, см. раздел 5.1: «корректность решения — не отдельная метрика, а главный компонент score») |
| `role` (`assessment`/`warmup`/`closing`) | — | `warmup`/`closing` **освобождены** от всего вышеперечисленного — не участвуют в вердикте вообще (раздел 2.3, шаги 3 и 6) |

Инвариант одной строкой (см. `specs/003-recruiter-vacancy-management/data-model.md`):
`role = assessment` ⇒ `intent`, `reference_answer`, `skill_tag[]` не пустые.

**Практическое следствие для промпта генерации вопросов**: LLM, которая генерирует
базовые вопросы (`backend/app/services/question_generation.py`, спека 003), должна
выдавать этот триплет **за один вызов вместе с текстом вопроса**, не отдельным шагом —
иначе рекрутёр может сохранить вопрос без эталона, и на выходе будет `untested` навык
вместо реальной оценки.

## 3. Шкала `score` — фиксированные якоря (раздел 5.1)

`score` — 0–100, **не выдумывается оценщиком заново каждый раз**, а привязан к якорям:

| Диапазон | Значение |
|---|---|
| 0–20 | Неверно / не по теме — конкретные фактические ошибки, решение не работает по существу |
| 21–40 | Очень слабо — почти нет релевантного содержания, либо решение принципиально не работает |
| 41–60 | Неполно/неуверенно — верное направление, но не хватает конкретики/части решения |
| 61–80 | Корректно и уверенно — решение работает / ответ по существу покрывает эталон |
| 81–100 | Отлично — решение работает и добавляет глубину сверх эталона |

Отдельной системы штрафов поверх этой шкалы нет — «неверно» уже занимает нижнюю часть,
это и есть штраф. Единственные два модификатора — ниже.

## 4. Модификаторы `score` (реализовано в `verdict.py`, `_effective_score`)

- **Штраф за подсказку** (`answered_with_hint=true`): `effective_score = min(score, 60)`.
  Ответ, до которого кандидат дошёл с наводящим вопросом (`dynamic_trigger=leading_hint`),
  физически не может попасть в диапазон «уверенное владение» (61+), сколько бы ни
  выставил оценщик за само содержание ответа.
- **`stretch`-бонус**: `stretch`-вопрос (заведомо сложнее базового уровня грейда, либо
  `drill_down`-вопрос — тот `stretch` по определению) **никогда не тянет навык в fail**,
  только даёт `stretch_bonus=true`, если эффективный score ≥ 60. Это отдельный флаг,
  не участвующий в агрегированном `effective_score` навыка — просто сигнал «уверенно», не
  четвёртый класс.

## 5. Агрегация по навыку (`aggregate_skills`, `verdict.py`)

Группировка идёт по `skill_tag`, дальше правило зависит от того, входит ли тег в
`required_skills` вакансии:

- **Обязательный навык** — **минимум** `effective_score` среди всех `baseline`-вопросов
  этого тега. `stretch`-вопросы в минимуме не участвуют вообще.
- **Дополнительный/общий навык** (nice-to-have или общая категория вроде «Алгоритмы») —
  **среднее** по `baseline`-вопросам.
- **Нет ни одного `baseline`-вопроса по тегу** → `untested`, не `fail`. Для обязательного
  навыка это тоже блокирует «подходит» (см. раздел 6), но семантически «не проверили», а
  не «провалил».

`SkillClass` по итоговому `effective_score` (`_classify`): `< 40` → `fail`; `40–59` →
`ambiguous`; `≥ 60` → `pass`. Пороги — рабочая гипотеза, требуют калибровки на реальных
интервью (см. открытые вопросы, раздел 10 архитектурного документа).

## 6. Формула вердикта (`compute_verdict`, приоритет сверху вниз)

1. Хоть один **обязательный** навык `fail` → **`not_fits`**.
2. Есть противоречие в ответах (`contradiction_check` сработал) → **`needs_review`** —
   не может быть «подходит», даже если все навыки в порядке.
3. Хоть один обязательный навык `ambiguous` **или** `untested` → **`needs_review`**.
4. Иначе → **`fits`**.

Дополнительные навыки в формулу вердикта **не входят напрямую** — только в
`overall_score` (отдельная взвешенная метрика для сортировки таблицы 2.5) и в «сильные
стороны» отчёта. Один общий балл специально не решает вердикт — иначе сильный
необязательный навык мог бы маскировать провал обязательного через усреднение.

## 7. Противоречия — отдельный сигнал, не skill-score

`contradiction_check` (тип адаптивного вопроса, раздел 2.3.1) не даёт `QuestionScore`
вообще — пишется как отдельный флаг `contradictions_found` и напрямую блокирует `fits`
(п.2 выше). Обоснование не техническое, а содержательное: недостоверность заявленного
опыта важнее отдельного правильного ответа — воспроизводит экспертную эвристику, не
статистику.

## 8. Чек-лист: данные, которые нужны агенту для качественной оценки

Свести всё выше в проверочный список — на что явно смотреть при генерации вопроса
(рекрутёром вручную или LLM-генератором), чтобы вопрос реально был оцениваемым:

- [ ] Есть `reference_answer` — не «на будущее», а прямо сейчас, до публикации вакансии
- [ ] `reference_answer` содержит конкретные проверяемые пункты, не общую формулировку
      («упомянул составной индекс и объяснил, почему seq scan» — не «хорошо ответил про
      индексы»)
- [ ] `skill_tag[]` заполнен и соответствует **конкретному** навыку из
      `required_skills`/`nice_to_have_skills` вакансии (сравнение по точному тегу, не по
      смыслу — если теги не совпадают дословно, навык не проверится вообще)
- [ ] Для многотегового вопроса (типично `live_coding`) — каждый тег действительно
      проверяется этим вопросом по отдельности, не «до кучи»
- [ ] `difficulty=stretch` проставлен осознанно (вопрос реально сложнее базового уровня
      грейда), а не по умолчанию — иначе он не должен считаться в минимум обязательного
      навыка, когда должен бы
- [ ] Для `format=live_coding` — есть не только текстовый `reference_answer`, но и
      эталонное решение + критерии (корректность, edge cases, сложность, стиль — раздел
      2.1.1); сама корректность решения — главный компонент `score`, не бонус
- [ ] `role` не перепутан: вступительный/закрывающий вопрос — `warmup`/`closing`, не
      `assessment` (иначе система потребует от него `reference_answer`, которого там
      осознанно нет)
